## How a run works

1. **Design.** Brainstorm with Mouhamed (one question at a time, approaches with a recommendation, design sections approved one by one). Write the design in `platform/` with a date prefix, add it to the context index (`README.md`, Live documents), update **Now**. Mouhamed reviews the written design before planning.
2. **Plan.** Write the plan in `platform/plans/`: base commit, branch, worktree, test database, facts with file and line references, tasks with checkboxes, a final controller task (review, the test and security audits, merge, walkthrough) naming the story IDs it walks, and an empty Outcome section. Put the plan link and that task in the run's row here (Plan, Stories) and in the run's section of `stories/09-agentic.md`.
3. **Build.** When the build starts, set the run's stories to `In progress (<run>)`. One branch and worktree per run (for A1: branch `a1-action-registry`, worktree `worktrees/a1-action-registry`), its own test database (`jendal_test_a1`; see Environment for the commands). One worker per task; the controller reviews each task and the whole branch. Checks per task: `npx vitest run <paths>`, `pnpm check-types`, `pnpm lint`. Conventional Commits ending with `Co-authored-by: factory-droid[bot] <138933559+factory-droid[bot]@users.noreply.github.com>`. Never push.
4. **Audit (required before every merge).** Run the `test-audit` skill over every test the branch adds or changes, then the `security-audit` skill in full audit mode with the `quick` profile, scoped to the run's diff (`origin/main...<branch>`), writing its output outside the repository (`~/security-audit-skill/payleor/run-<N>`). Record both in the plan's Outcome (removed or kept tests and why; confirmed findings, needs-validation items, and the coverage the run did not claim). Confirmed findings are fixed on the branch, or become backlog rows with an owner, before the merge. A plan's final controller task names both audits.
5. **Merge.** `git merge --no-ff` into main, `pnpm install`, `pnpm db:migrate:dev` (check the dev data before and after), restart the dev stack.
6. **Walkthrough.** Run the plan's stories from [`stories/`](stories/README.md) in the PayPal sandbox with a browser agent (Playwright, Chrome DevTools or Claude in Chrome): on staging (`staging.payleor.com`, `dash.staging.payleor.com`, `api.staging.payleor.com`, `*.staging.payleor.app`, deployed by hand from the branch) before the merge, and on production after it. Mouhamed does the [human] steps (paying in the PayPal popup, Payouts Web uploads, plugin connectors, Discord accounts). Fixes found go in a follow-up branch.
7. **Record.** Fill the plan's Outcome, set the design's status, update the stories' statuses (and add stories for new features), move finished backlog rows to [`archive/backlog-done.md`](archive/backlog-done.md) and add new findings to Open, update the run board, **Now** and the context index, and [`platform/2026-10-16-architecture.md`](platform/2026-10-16-architecture.md) when the run changed hosts, bindings, packages, money flows or surfaces. Remove the worktree, branch and test database. A run is not marked done on the board until its plan's Outcome is filled in; then move the plan and its evidence to `archive/platform/plans/` (see the README's "Keeping this index useful").

Spec and plan edits normally land on main (`docs(specs): …`). **Exception approved by Mouhamed, 2026-10-28:** commit this contextual-agent scope/docs update on `b1-operating-model`, alongside B1's existing spec changes. This does not authorize a merge or push.

The agent tooling named in plans (writing-plans, subagent-driven-development, explorer and worker subagents, Playwright and Chrome DevTools for walkthroughs) are Droid skills and subagents. A person can follow the same steps by hand: the plan's tasks are self-contained.
