# S2: Discord Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Payleor user signs in with Discord on the web and links Discord in Account settings. A services team admin creates a one-time link code in the team admin and runs `/payleor link code:…` in their Discord server; the bot checks the caller's Manage Server permission and that their Discord account belongs to a Payleor admin of that team, then stores the guild on the team and the setup checklist's "Link Discord" step becomes done. Anyone runs `/payouts setup` and gets an ephemeral link to the freelancer portal's payout destination page at `admin.<domain>/me/payouts`, where "Log in with PayPal" stores a verified `payout_destination` row. The api Worker answers Ed25519-verified interactions at `POST /discord/interactions` — PONG for PING, immediate replies for instant answers, deferred responses plus follow-ups through the interaction webhook for anything that can exceed Discord's 3-second limit — and `pnpm -F server discord:register` publishes the global command registry.

**Architecture:** Five `DISCORD_*` keys (`DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_APP_ID`, `DISCORD_PUBLIC_KEY`, `DISCORD_BOT_TOKEN`, already filled in by the user in `apps/server/.env`) flow through the server's varlock schema (`apps/server/.env.schema`), the infra schema's `@import(../../apps/server/, pick=[...])` list (`packages/infra/.env.schema`, which reads the values from `apps/server/.env`, so no `.env` file is edited), `alchemy.run.ts` and `turbo.json`. `@jendal-workspace/core` gains `discordGuildId` on `ServicesTeamSettings` and the setup-step state, a test proving no slug can be `me`, and the payout-destination draft built from PayPal's userinfo response. `packages/db` adds the `services_team_settings.discord_guild_id` column and the `discord_link_code` and `payout_destination` tables, plus a `discord` repository (link codes, Discord-ID lookup, guild linking) and a `payouts` repository (destination read/save, linked PayPal account lookup). `packages/auth` turns on Better Auth's Discord provider and explicit account linking with a different email for signed-in users, without trusted providers (Fact 22). The tRPC API adds `payoutDestination.{get,connect}` (connect asks PayPal's userinfo endpoint for the payer ID with the linked PayPal account's access token, Fact 14) and `servicesTeam.createDiscordLinkCode`. The api Worker gets `apps/server/src/discord/{verify,commands,interactions,rest,route,register}.ts`: `verify` checks Ed25519 with Web Crypto, `commands` is the registry, `interactions` dispatches (PONG, immediate `/payouts setup`, deferred `/payleor link` whose result is PATCHed through the interaction webhook), `rest` posts and edits channel messages with the bot token for later plans, `route` wires it into Hono with its own database connection for the deferred follow-up, and `register` is the bun script (run through `varlock run`, Fact 21) that bulk-puts the global commands. The web app gets "Continue with Discord" on login and signup, the Account page with "Link Discord", the team admin's "Link Discord" page, and `/me/payouts`.

## Facts this plan relies on

Each was checked against the pinned sources, the live Discord and Cloudflare documentation, or the repository on 2026-10-06. If code fails in a way that contradicts one of them, re-read the cited source before changing the design.

Discord documentation (all fetched 2026-10-06):

1. **Signature verification.** Every interaction request carries `X-Signature-Ed25519` (hex signature) and `X-Signature-Timestamp`; the app must verify the signature over `timestamp + raw body` with the app's Ed25519 public key (hex, from the developer portal) and answer `401` on failure. Discord also sends deliberate bad signatures routinely and removes the endpoint URL if it accepts them. https://discord.com/developers/docs/interactions/overview, section "Validating Security Request Headers".
2. **PING.** Before Discord saves the Interactions Endpoint URL it sends a `type: 1` PING; the endpoint must answer `200` with a `{"type": 1}` PONG and a JSON content type. Same page, section "Acknowledging PING requests".
3. **Interaction and callback types.** Interaction types: PING `1`, APPLICATION_COMMAND `2`, MESSAGE_COMPONENT `3`, APPLICATION_COMMAND_AUTOCOMPLETE `4`, MODAL_SUBMIT `5`. Callback types: PONG `1`, CHANNEL_MESSAGE_WITH_SOURCE `4`, DEFERRED_CHANNEL_MESSAGE_WITH_SOURCE `5`, APPLICATION_COMMAND_AUTOCOMPLETE_RESULT `8`. The interaction's `member` (guild invocations) includes the invoking user's `permissions`; `user` is sent for DM invocations; `guild_id` names the guild; `data.options` carries the command's option values. https://discord.com/developers/docs/interactions/receiving-and-responding, sections "Interaction Object", "Interaction Data", "Application Command Interaction Data Option Structure".
4. **The 3-second limit and follow-ups.** The initial response must be sent within 3 seconds of the interaction or the token is invalidated; the token itself lives 15 minutes. A deferred response is edited with `PATCH /webhooks/{application.id}/{interaction.token}/messages/@original`, which needs no bot token. Same URL, sections "Interaction Callback" and "Followup Messages" (including "Edit Original Interaction Response").
5. **Ephemeral.** The `EPHEMERAL` message flag is `1 << 6` (64); on a `DEFERRED_CHANNEL_MESSAGE_WITH_SOURCE` callback the only valid flag is `EPHEMERAL`. Same URL, sections "Interaction Callback Data Structure" (flags) and "Interaction Callback Type" (defer).
6. **Command registration.** Global commands are registered at `POST /applications/{application_id}/commands` (a POST with an already-used name updates it) or `PUT /applications/{application_id}/commands` (bulk overwrite of the whole global list, returns `200` and the command list), with `Authorization: Bot <token>`. Option types: `SUB_COMMAND` = 1, `STRING` = 3; required options must be listed before optional ones; `STRING` options accept `min_length`/`max_length`. Command descriptions are 1–100 characters. https://discord.com/developers/docs/interactions/application-commands, sections "Registering a Command", "Application Command Structure", "Application Command Option Structure", "Application Command Option Type", "Bulk Overwrite Global Application Commands". The `Authorization: Bot TOKEN` header format is in https://discord.com/developers/docs/reference, section "Authentication"; API version 10 is available and current (same page, "API Versioning").
7. **Manage Server.** `MANAGE_GUILD` is `1 << 5` (`0x20`); permissions are serialized as strings and checked by bitwise AND (BigInt, since values exceed 2^53). https://discord.com/developers/docs/topics/permissions, sections "Bitwise Permission Flags" and the intro paragraph.
8. **Channel messages.** Create Message is `POST /channels/{channel.id}/messages`; Edit Message is `PATCH /channels/{channel.id}/messages/{message.id}`; both take `content`, `embeds`, `components` and return the message object. https://discord.com/developers/docs/resources/message, sections "Create Message" and "Edit Message".

Cloudflare and Node:

9. **Ed25519 in Web Crypto.** workerd: "The Web Crypto API now supports curves Ed25519 and X25519 defined in the Secure Curves specification" (changelog entry 2023-04-28) — https://developers.cloudflare.com/workers/platform/changelog/. Node on this machine is v24.12.0 and `crypto.subtle.generateKey({ name: "Ed25519" })`, `sign`, `verify` and `importKey("raw", …)` all work with 32-byte raw public keys (verified on this machine, 2026-10-06), so the tests can generate their own Ed25519 key pair and sign a timestamp+body.

Better Auth (`refs/stack/better-auth`):

10. **Discord provider.** `refs/stack/better-auth/packages/core/src/social-providers/discord.ts:87-101`: `id: "discord"`, `accountSubject: ({ profile }) => profile.id` (the Discord snowflake becomes the account's `accountId`), default scopes `["identify", "email"]`, authorization endpoint `https://discord.com/api/oauth2/authorize`, token endpoint `https://discord.com/api/oauth2/token`. `getUserInfo` maps `global_name`/`username`, `email` and `emailVerified: profile.verified`, then merges `mapProfileToUser` (`discord.ts:159-168`). Discord accounts can have an unverified email (`verified: false`). The provider has no `verifyIdToken`, so `linkSocial`'s direct id-token branch rejects it (the PayPal provider has none either).
11. **`linkSocial`.** `POST /link-social` has `requireHeaders: true` (`packages/better-auth/src/api/routes/account.ts:130`; a server call without `headers` fails body validation before the session check) and `use: [sessionMiddleware]` (`account.ts:215`), takes `provider`, `callbackURL`, `errorCallbackURL`, `disableRedirect` (body schema, `account.ts:131-214`) and returns `{ url, redirect }` (`account.ts:447-450`). The endpoint is exported as `linkSocialAccount` (`account.ts:126`), so the server-side methods are `auth.api.linkSocialAccount` and `auth.api.listAccounts` (`GET /list-accounts`, `account.ts:53-125`); the browser client calls the same endpoint as `authClient.linkSocial` (the client derives its method names from the path).
12. **The client follows the redirect.** Any client response with `{ url, redirect: true }` sets `window.location.href` — `packages/better-auth/src/client/fetch-plugins.ts:8-27`. So `authClient.signIn.social` and `authClient.linkSocial` both navigate on success and the button stays disabled.
13. **Explicit linking rules.** `linkOAuthAccount` (the OAuth callback's `if (link)` branch for a signed-in user) refuses an untrusted provider whose email is not verified (`packages/better-auth/src/oauth2/link-account.ts:92-104`) and refuses a provider email that differs from the session user's unless `account.accountLinking.allowDifferentEmails` is true (`link-account.ts:106-114`); `trustedProviders` defaults to empty (`packages/better-auth/src/context/helpers.ts:296-306`); `updateUserInfoOnLink` is off by default (`link-account.ts:711-731`). The callback redirects to `callbackURL` after a successful link and to `errorCallbackURL` with `?error=<code>` on failure (`packages/better-auth/src/api/routes/callback.ts:268-280`). `allowDifferentEmails` is read only by explicit linking (`link-account.ts:107`, `account.ts:384`), never by sign-in.
14. **PayPal account identity and the payer ID.** `refs/stack/better-auth/packages/core/src/social-providers/paypal.ts:96`: `accountSubject: ({ profile }) => profile.user_id`. PayPal's `user_id` is the Log In with PayPal subject URL (`https://www.paypal.com/webapps/auth/identity/user/<id>`), **not** the payer ID; the payer ID is the separate `payer_id` userinfo field (`PayPalProfile`, `paypal.ts:16-44`), returned when the app requests the `https://uri.paypal.com/services/paypalattributes` scope, which `packages/auth/src/paypal.ts` already puts on the authorize URL. Payouts with `recipient_type: PAYPAL_ID` need that payer ID, "the encrypted PayPal account number", e.g. `G83JXTJ5EHCQ2` (`refs/paypal/paypal-rest-api-specifications/openapi/payments_payouts_batch_v1.json`). Better Auth does not store the userinfo profile, so the payer ID must be read from `GET https://api-m.sandbox.paypal.com/v1/identity/oauth2/userinfo?schema=paypalv1.1` (`https://api-m.paypal.com/...` live; the URLs Better Auth itself uses, `paypal.ts:82-84, 175-183`) with the linked account's access token. `auth.api.getAccessToken({ body: { accountId, userId } })` without headers returns that token, decrypted and refreshed if needed (`account.ts:527-545, 640-754`); Better Auth stores tokens raw unless `encryptOAuthTokens` is set (`packages/better-auth/src/oauth2/utils.ts:12-37`).

Repository:

16. **Static routes beat the dynamic slug route, and no slug can be `me`.** `app/admin/new/page.tsx` already coexists with `app/admin/[storeSlug]/page.tsx`, so `/admin/account` and `/admin/me/payouts` win over `/{slug}`. `RESERVED_SLUGS` in `packages/core/src/tenancy/slug.ts` already reserves `account`. `me` needs no reservation: `SLUG_PATTERN` (`/^[a-z0-9][a-z0-9-]{1,38}[a-z0-9]$/`, same file) requires at least three characters and is checked before the reserved list, so `validateStoreSlug("me")` already returns `{ ok: false, reason: "format" }`. Task 2 pins that with a test instead of adding `me` to the list (a reserved-list test for `me` would fail, since the format check answers first).
17. **Env plumbing.** `apps/server/.env.schema` drives the generated (gitignored) `apps/server/src/env.ts` via varlock (`pnpm env:generate`, also `postinstall`); each key appears there twice (a doc-comment line `* **KEY**` and a typed line `KEY: string;`), and public keys once more in `PublicCoercedEnvSchema`. `packages/infra/.env.schema` starts with `# @import(../../apps/server/, pick=[...])`: varlock loads the picked keys' schema **and values** from `apps/server/` (the user's `packages/infra/.env` holds only `TUNNEL_DOMAIN`, `TUNNEL_STAGE` and `DEV_DATABASE_URL`, while `PAYPAL_CLIENT_ID` and the other server keys reach infra through the import), so a new server key needs only to join the pick list, never a value in `packages/infra/.env`. `alchemy.run.ts` (which loads env through `import "varlock/auto-load"`) passes each key to the Worker env, and `ENV` in `apps/server/src/env.server.ts` is typed from it (`apps/server/cloudflare-env.d.ts` → `ServerEnv`); `turbo.json` `globalEnv` lists keys alphabetically. So a new server key goes into the server schema, the infra pick list, `alchemy.run.ts` and `turbo.json`.
18. **Tests.** `vitest.config.ts` loads `.env.test.local`, includes `apps/server/src/**/*.test.ts` and `packages/*/src/**/*.test.ts`, runs files one at a time (shared database), and sets `testTimeout: 20_000`. DB-dependent suites gate on `hasTestDatabase`; the global setup re-creates the test database from every migration, so a new migration is applied by running the tests.
19. **One connection per client; the middleware closes its db with the response.** `createDb` uses `postgres(..., { max: 1 })` (`packages/db/src/index.ts`) and the api Worker's `app.use("*")` middleware closes its db with `waitUntil(db.$client.end())` after `next()` returns (`apps/server/src/index.ts`). A deferred follow-up therefore gets its own connection opened by the route and closed with the follow-up, so it cannot race the middleware's close.
20. **W1-D execution notes still apply.** Packages that import `drizzle-orm` in tests must declare it (this plan's tests import only schema and repository modules, so no new dependency is needed); vitest's timeout is already 20 s. The shared `tsconfig.base.json` sets `noUnusedLocals` and `noUnusedParameters`, so an unused import or constant is a type error (TypeScript 6.0.3).
21. **bun does not load `.env` in `apps/server`.** `apps/server/bunfig.toml` is `env = false`, so `bun src/discord/register.ts` alone sees no `DISCORD_*` values. `varlock run -- <command>` (varlock is already an `apps/server` dependency; `packages/infra`'s `db:migrate:dev` uses the same pattern) loads and validates `apps/server/.env` against the schema and injects the values without printing them. bun 1.3.4 is installed at `/home/mouhamed/.bun/bin/bun` (checked with `which bun` on 2026-10-06).
22. **Implicit linking and `trustedProviders` (account takeover).** On social **sign-in** (not linking), `handleOAuthUserInfo` looks the user up by the provider's email and links the new provider account to that existing user when the provider is in `trustedProviders` **or** the provider email is verified, and the local user's email is verified (`packages/better-auth/src/oauth2/link-account.ts:249-306`). With `trustedProviders: ["discord"]`, anyone who creates a Discord account with a victim's address (Discord does not require it to be verified) and clicks "Continue with Discord" would be linked into, and signed in as, the victim's Payleor account. The same applies to PayPal. So this plan sets **no** trusted providers: implicit linking then requires the provider to report the email verified, as today for PayPal. `allowDifferentEmails: true` is safe because only explicit linking reads it (Fact 13): the user already holds a Payleor session and proves the Discord or PayPal identity through OAuth with state bound to that session. Explicit linking without trusted providers requires a verified Discord (or PayPal) email (Fact 13).

`packages/core/src/payouts/destination.ts`:

```ts
export type PayoutDestinationDraft = { paypalPayerId: string; paypalEmail: string | null };

type PayPalEmailEntry = { value?: unknown; primary?: unknown; confirmed?: unknown };

type PayPalUserInfo = {
  user_id?: unknown;
  payer_id?: unknown;
  email?: unknown;
  email_verified?: unknown;
  emails?: unknown;
};

// PAYPAL_ID payouts take "the encrypted PayPal account number" (e.g. G83JXTJ5EHCQ2, Fact 14).
const PAYER_ID_PATTERN = /^[0-9A-Z]{13}$/;

function verifiedEmail(info: PayPalUserInfo): string | null {
  if (typeof info.email === "string") return info.email_verified === true ? info.email : null;
  if (!Array.isArray(info.emails)) return null;
  const entries = info.emails as PayPalEmailEntry[];
  const entry = entries.find((candidate) => candidate.primary === true) ?? entries[0];
  return entry && typeof entry.value === "string" && entry.confirmed === true ? entry.value : null;
}

// `userInfo` is PayPal's own userinfo response, fetched server-side with the linked account's access
// token, so nothing here comes from the user. Its user_id must be the account ID Better Auth stored
// for the linked PayPal account; the payer ID is a separate field (Fact 14).
export function payoutDestinationFromUserInfo(
  paypalAccountId: string,
  userInfo: unknown,
): PayoutDestinationDraft | null {
  if (typeof userInfo !== "object" || userInfo === null) return null;
  const info = userInfo as PayPalUserInfo;
  if (info.user_id !== paypalAccountId) return null;
  if (typeof info.payer_id !== "string" || !PAYER_ID_PATTERN.test(info.payer_id)) return null;
  return { paypalPayerId: info.payer_id, paypalEmail: verifiedEmail(info) };
}

// A one-time code an admin creates in the team admin and runs as /payleor link code:… (services spec §4.2).
export async function createDiscordLinkCode(
  db: Database,
  teamId: string,
  { minutes = 15 }: { minutes?: number } = {},
): Promise<DiscordLinkCode> {
  const expiresAt = new Date(Date.now() + minutes * 60_000);
  const code = crypto.randomUUID().replaceAll("-", "").slice(0, 12);
  await db.insert(discordLinkCode).values({ teamId, code, expiresAt });

    .delete(discordLinkCode)
    .where(and(eq(discordLinkCode.code, code), gt(discordLinkCode.expiresAt, new Date())))
    .returning({ teamId: discordLinkCode.teamId });
  return rows[0]?.teamId ?? null;
}

export async function setServicesTeamDiscordGuildId(
  db: Database,
  teamId: string,
  guildId: string,

    .update(servicesTeamSettings)
    .set({ discordGuildId: guildId })
    .where(eq(servicesTeamSettings.teamId, teamId))
    .returning({ teamId: servicesTeamSettings.teamId });

// never user input, so every saved row is a verified destination (services spec §4.2).
export async function savePayoutDestination(
  db: Database,
  userId: string,
  draft: PayoutDestinationDraft,
): Promise<PayoutDestinationRecord> {
  const values = { ...draft, verifiedAt: new Date() };
  const [row] = await db
    .insert(payoutDestination)
    .values({ userId, ...values })
    .onConflictDoUpdate({ target: payoutDestination.userId, set: values })
    .returning(destinationColumns);
  if (!row) throw new Error("Upsert into payout_destination returned no row");

// "Log in with PayPal" (sign-up, sign-in or linkSocial) writes this Better Auth account row: `id` is
// the row ID getAccessToken takes, `accountId` is PayPal's user_id, not the payer ID (Fact 14).
// A PayPal account belongs to one Payleor user, but one user can link several PayPal accounts; the
// most recently updated row is the one the user just linked or signed in with.
export async function findLinkedPayPalAccount(
  db: Database,
  userId: string,
): Promise<{ id: string; accountId: string } | null> {
  const [row] = await db
    .select({ id: account.id, accountId: account.accountId })
    .from(account)
    .where(and(eq(account.providerId, "paypal"), eq(account.userId, userId)))
    .orderBy(desc(account.updatedAt))
    .limit(1);
  return row ?? null;
}

// tRPC has no transformer here, so dates are returned as ISO strings (as servicesTeam.get does).
function shaped(record: { paypalPayerId: string; paypalEmail: string | null; verifiedAt: Date }) {
  return {
    paypalPayerId: record.paypalPayerId,
    paypalEmail: record.paypalEmail,
    verifiedAt: record.verifiedAt.toISOString(),
  };
}

function unconfirmed(): TRPCError {
  return new TRPCError({
    code: "PRECONDITION_FAILED",
    message: "PayPal did not confirm your payer ID. Connect PayPal again.",
  });
}

export const payoutDestinationRouter = router({
  get: protectedProcedure.query(async ({ ctx }) => {
    const destination = await getPayoutDestination(ctx.db, ctx.session.user.id);
    return destination ? shaped(destination) : null;
  }),

  // Runs after "Log in with PayPal" returns the user to /me/payouts. Takes no input: the payer ID and
  // email come only from PayPal's userinfo for the account PayPal linked (services spec §4.2, Fact 14).
  connect: protectedProcedure.mutation(async ({ ctx }) => {
    const userId = ctx.session.user.id;
    const linked = await findLinkedPayPalAccount(ctx.db, userId);
    if (!linked) {
      throw new TRPCError({
        code: "PRECONDITION_FAILED",
        message: "Connect PayPal first, then come back to this page.",
      });
    }
    // Server-side call without headers: Better Auth acts for `userId`, decrypting and refreshing the
    // stored token as needed (Fact 14). The account row was found for this same user above.
    const tokens = await ctx.auth.api
      .getAccessToken({ body: { accountId: linked.id, userId } })

// Discord signs every interaction request with Ed25519 over "<timestamp><raw body>" and hex-encodes
// signature and public key (Fact 1). workerd's Web Crypto supports Ed25519 (Fact 9).
const encoder = new TextEncoder();

const HEX_PATTERN = /^(?:[0-9a-f]{2})+$/i;

// The pattern check matters: Number.parseInt("1g", 16) is 1, so a per-pair parse alone would accept junk.
export function hexToBytes(hex: string): Uint8Array<ArrayBuffer> {
  if (!HEX_PATTERN.test(hex)) throw new Error("Not a hex string");
  const bytes = new Uint8Array(hex.length / 2);
  for (let index = 0; index < bytes.length; index++) {
    bytes[index] = Number.parseInt(hex.slice(index * 2, index * 2 + 2), 16);
  }
  return bytes;
}

// Never throws: any malformed input is simply a request we cannot trust, so the caller answers 401.
export async function verifyDiscordSignature(
  publicKeyHex: string,
  timestamp: string,
  body: string,
  signatureHex: string,
): Promise<boolean> {
  try {
    const key = await crypto.subtle.importKey("raw", hexToBytes(publicKeyHex), { name: "Ed25519" }, false, ["verify"]);
    return await crypto.subtle.verify(
      { name: "Ed25519" },
      key,
      hexToBytes(signatureHex),
      encoder.encode(timestamp + body),
    );
  } catch {
    return false;
  }
}

import { canServicesTeam } from "@jendal-workspace/core";
import type { Database } from "@jendal-workspace/db";
import {
  consumeDiscordLinkCode,
  findUserIdByDiscordId,
  setServicesTeamDiscordGuildId,
} from "@jendal-workspace/db/repositories/discord";
import { servicesTeamRoleFor } from "@jendal-workspace/db/repositories/services-teams";

// Interaction types (Fact 3). Only PING, commands and autocomplete arrive today; components and
// modals come with later plans (services spec §8.4) and get the polite default meanwhile.
const INTERACTION_PING = 1;
const INTERACTION_APPLICATION_COMMAND = 2;
const INTERACTION_AUTOCOMPLETE = 4;

// Callback types (Fact 3): 4 answers at once, 5 defers within the 3-second limit (Fact 4), 8 answers
// autocomplete, 1 answers a PING.
const CALLBACK_PONG = 1;
const CALLBACK_CHANNEL_MESSAGE_WITH_SOURCE = 4;
const CALLBACK_DEFERRED_CHANNEL_MESSAGE_WITH_SOURCE = 5;
const CALLBACK_AUTOCOMPLETE_RESULT = 8;

// Only the invoking user sees the reply (Fact 5).
const EPHEMERAL = 1 << 6;
// Required in the guild before a server link is accepted (Fact 7).
const MANAGE_GUILD = 1 << 5;

const DISCORD_API = "https://discord.com/api/v10";

export type DiscordInteractionOption = {
  name: string;
  type: number;
  value?: string;
  options?: DiscordInteractionOption[];
};

// Only the fields Payleor reads (Fact 3): the invoker as member (guild) or user (DM), the guild,
// the command data and the interaction token.
export type DiscordInteraction = {
  id: string;
  token: string;
  type: number;
  data?: { name?: string; options?: DiscordInteractionOption[] };
  guild_id?: string;
  member?: { user: { id: string }; permissions?: string };
  user?: { id: string };
};

export type DiscordConfig = {
  applicationId: string;
  // The admin origin (BETTER_AUTH_URL); /payouts setup links to /me/payouts there.
  webBaseUrl: string;
};

export type InteractionResponse = { type: number; data?: { content?: string; flags?: number; choices?: unknown[] } };

// The route's answer for a deferred result; only EPHEMERAL is valid on a defer (Fact 5).
export const DEFERRED_EPHEMERAL_RESPONSE: InteractionResponse = {
  type: CALLBACK_DEFERRED_CHANNEL_MESSAGE_WITH_SOURCE,
  data: { flags: EPHEMERAL },
};

export type InteractionResult =
  | { kind: "reply"; response: InteractionResponse }
  | { kind: "deferred"; followUp: Promise<string> };

function ephemeral(content: string): InteractionResult {
  return {
    kind: "reply",
    response: { type: CALLBACK_CHANNEL_MESSAGE_WITH_SOURCE, data: { flags: EPHEMERAL, content } },
  };
}

export async function handleDiscordInteraction(
  config: DiscordConfig,
  services: { db: Database },
  interaction: DiscordInteraction,
): Promise<InteractionResult> {
  switch (interaction.type) {
    case INTERACTION_PING:
      // Discord only saves the endpoint URL after a PING is acknowledged (Fact 2).
      return { kind: "reply", response: { type: CALLBACK_PONG } };
    case INTERACTION_APPLICATION_COMMAND:
      return dispatchCommand(config, services, interaction);
    case INTERACTION_AUTOCOMPLETE:
      return { kind: "reply", response: { type: CALLBACK_AUTOCOMPLETE_RESULT, data: { choices: [] } } };
    default:
      return ephemeral("Payleor cannot handle this interaction yet.");
  }
}

function subcommand(interaction: DiscordInteraction): {
  name: string;
  option: (optionName: string) => string | undefined;
} {
  const command = interaction.data?.options?.find((candidate) => candidate.type === 1);
  return {
    name: command?.name ?? "",
    option: (optionName) => command?.options?.find((candidate) => candidate.name === optionName)?.value,
  };
}

function dispatchCommand(
  config: DiscordConfig,
  services: { db: Database },
  interaction: DiscordInteraction,
): InteractionResult {
  const command = interaction.data?.name ?? "";
  const sub = subcommand(interaction);
  if (command === "payouts" && sub.name === "setup") {
    return ephemeral(`Set up your PayPal payout destination on Payleor: ${config.webBaseUrl}/me/payouts`);
  }
  if (command === "payleor" && sub.name === "link") {
    // Linking a server touches the database, so it may pass the 3-second window: the reply defers
    // (only EPHEMERAL is valid on a defer, Fact 5) and the route edits the original response with
    // the follow-up (Fact 4). Expected failures resolve into user-facing messages here; anything
    // unexpected rejects and the route posts a fallback.
    return {
      kind: "deferred",
      followUp: linkServer(config, services, interaction, sub.option("code") ?? ""),
    };
  }
  return ephemeral("Payleor does not know this command. Run /payleor link or /payouts setup.");
}

async function linkServer(
  config: DiscordConfig,
  services: { db: Database },
  interaction: DiscordInteraction,
  code: string,
): Promise<string> {
  const guildId = interaction.guild_id;
  const discordId = interaction.member?.user.id;
  const permissions = interaction.member?.permissions;
  if (!guildId || !discordId) {
    return "Run this command in the server you want to link to your Payleor team.";
  }
  if (typeof permissions !== "string" || (BigInt(permissions) & BigInt(MANAGE_GUILD)) !== BigInt(MANAGE_GUILD)) {
    return "You need the Manage Server permission in this server to link it to Payleor.";
  }
  // Consumed first and atomically, so the one-time code cannot be raced or replayed.
  const teamId = await consumeDiscordLinkCode(services.db, code);
  if (!teamId) {
    return "That code is not valid. An admin of your team creates a link code in the team admin on Payleor.";
  }
  const userId = await findUserIdByDiscordId(services.db, discordId);
  if (!userId) {
    return `First, link your Discord account to Payleor in Account settings (${config.webBaseUrl}/account), then run the command again.`;
  }
  const role = await servicesTeamRoleFor(services.db, teamId, userId);
  if (!canServicesTeam(role, "manage_connections")) {
    return "Your Payleor account is not an admin of that team, so it cannot link the server.";
  }
  const result = await setServicesTeamDiscordGuildId(services.db, teamId, guildId);
  if (result === "conflict") {
    return "Another Payleor team is already linked to this server.";
  }
  if (result === "missing") {
    return "Your team's settings are missing on Payleor. Open the team admin and try again.";
  }
  return "This server is now linked to your Payleor team. The Link Discord step in your team's setup checklist is done.";
}

// Edits the deferred original response through the interaction webhook; no bot token needed (Fact 4).
export async function editOriginalInteractionResponse(
  config: DiscordConfig,
  token: string,
  message: { content: string },
  fetchImpl: typeof fetch = fetch,
): Promise<void> {
  const response = await fetchImpl(`${DISCORD_API}/webhooks/${config.applicationId}/${token}/messages/@original`, {
    method: "PATCH",
    headers: { "content-type": "application/json" },
    body: JSON.stringify(message),
  });
  if (!response.ok) {
    throw new Error(`Editing the interaction response failed: ${response.status}`);
  }
}

// Discord REST helper for the bot token (contract §4.3). Later plans post and edit ticket cards with
// it; the interactions webhook calls live in interactions.ts because they need no token.
const DISCORD_API = "https://discord.com/api/v10";

export type DiscordChannelMessage = {
  content?: string;
  allowed_mentions?: { parse: [] };
  // Later plans add embeds and components for ticket cards (spec §5.2).
  embeds?: unknown[];
  components?: unknown[];
};

export type DiscordRest = {
  postChannelMessage(channelId: string, message: DiscordChannelMessage): Promise<unknown>;
  editChannelMessage(channelId: string, messageId: string, message: DiscordChannelMessage): Promise<unknown>;
};

export function createDiscordRest(input: { token: string; fetch?: typeof fetch }): DiscordRest {
  const fetchImpl = input.fetch ?? fetch;
  const headers = { authorization: `Bot ${input.token}`, "content-type": "application/json" };

  async function call(method: string, path: string, body: DiscordChannelMessage): Promise<unknown> {
    const response = await fetchImpl(`${DISCORD_API}${path}`, {
      method,
      headers,
      body: JSON.stringify(body),
    });
    if (!response.ok) {
      throw new Error(`Discord ${method} ${path} failed: ${response.status}`);
    }
    return response.status === 204 ? null : await response.json();
  }

  return {
    // Create Message: POST /channels/{channel.id}/messages.
    postChannelMessage(channelId, message) {
      return call("POST", `/channels/${channelId}/messages`, message);
    },
    // Edit Message: PATCH /channels/{channel.id}/messages/{message.id}.
    editChannelMessage(channelId, messageId, message) {
      return call("PATCH", `/channels/${channelId}/messages/${messageId}`, message);
    },
  };
}

import { log } from "evlog";
import { Hono } from "hono";

import { ENV } from "../env.server";
import { getDb } from "../services";
import type { AppEnv } from "../app-env";
import {
  DEFERRED_EPHEMERAL_RESPONSE,
  type DiscordConfig,
  type DiscordInteraction,
  editOriginalInteractionResponse,
  handleDiscordInteraction,
} from "./interactions";
import { verifyDiscordSignature } from "./verify";

const config: DiscordConfig = {
  applicationId: ENV.DISCORD_APP_ID,
  webBaseUrl: ENV.BETTER_AUTH_URL,
};

export const discordRoute = new Hono<AppEnv>().post("/discord/interactions", async (c) => {
  const timestamp = c.req.header("x-signature-timestamp") ?? "";
  const signature = c.req.header("x-signature-ed25519") ?? "";
  const body = await c.req.text();
  if (!(await verifyDiscordSignature(ENV.DISCORD_PUBLIC_KEY, timestamp, body, signature))) {
    // Discord expects 401 for an invalid signature (Fact 1).
    return c.text("invalid request signature", 401);
  }

  // The deferred follow-up needs the database after the response is sent, and the global middleware
  // closes its db with the request (Fact 19), so the follow-up gets its own connection, opened here
  // and closed with it.
  const db = getDb();
  try {
    const interaction = JSON.parse(body) as DiscordInteraction;
    const result = await handleDiscordInteraction(config, { db }, interaction);
    if (result.kind === "reply") {
      await db.$client.end();
      return c.json(result.response);
    }
    c.executionCtx.waitUntil(
      (async () => {
        try {
          const content = await result.followUp.catch((error: unknown) => {
            log.error({
              action: "discord.followup",
              error: { name: error instanceof Error ? error.name : typeof error },
            });
            return "Something went wrong. Please run the command again.";
          });
          await editOriginalInteractionResponse(config, interaction.token, { content });
        } catch (error) {
          log.error({
            action: "discord.followup",
            error: { name: error instanceof Error ? error.name : typeof error },
          });
        } finally {
          await db.$client.end().catch(() => undefined);
        }
      })(),
    );
    return c.json(DEFERRED_EPHEMERAL_RESPONSE);
  } catch (error) {
    await db.$client.end().catch(() => undefined);
    throw error;
  }
});

    if (!connect || connectAttempted || destination.isPending || destination.data) return;
    setConnectAttempted(true);
    save.mutate();
  }, [connect, connectAttempted, destination.isPending, destination.data, save.mutate]);

  async function connectPayPal() {
    setLinkPending(true);
    const result = await authClient.linkSocial({
      provider: "paypal",
      callbackURL: "/me/payouts?connect=1",
      errorCallbackURL: "/me/payouts?error=1",
    });
    if (result.error) {
      setLinkPending(false);
      toast.error(result.error.message ?? "Could not start PayPal.");
    }
    // On success the client follows the redirect to PayPal, so the button stays disabled.
  }

  if (destination.isPending) return <Loader />;

  return (
    <main className="container mx-auto max-w-lg space-y-6 px-4 py-10">
      <h1 className="text-2xl font-semibold tracking-tight">Payouts</h1>
      {paypalError ? (
        <p role="alert" className="border border-destructive p-3 text-sm text-destructive">
          PayPal did not confirm the connection. Try again.
        </p>
      ) : null}
      <section aria-labelledby="destination-heading" className="space-y-3 border p-4">
        <h2 id="destination-heading" className="font-medium">
          Your PayPal payout destination
        </h2>
        {destination.data ? (
          <div className="space-y-2 text-sm text-muted-foreground">
            <p>
              Verified PayPal account{destination.data.paypalEmail ? ` (${destination.data.paypalEmail})` : ""}. Payer
              ID {destination.data.paypalPayerId}.
            </p>
            <p>
              Verified {destination.data.verifiedAt ? new Date(destination.data.verifiedAt).toLocaleString() : "recently"}
              . Teams pay you with this PayPal account.
            </p>
          </div>
        ) : (
          <>
            <p className="text-sm text-muted-foreground">
              Connect your PayPal account once. Payleor stores your PayPal payer ID; teams pay you with it.
            </p>
            {save.isError ? (
              <p role="alert" className="text-sm text-destructive">
                {save.error.message}
              </p>
            ) : null}
            {save.isSuccess ? (
              <p className="text-sm text-emerald-700 dark:text-emerald-400">PayPal destination saved.</p>
            ) : null}
            <Button type="button" variant="outline" onClick={connectPayPal} disabled={linkPending}>
              {linkPending ? "Redirecting to PayPal…" : "Log in with PayPal"}
            </Button>
          </>
        )}
      </section>
    </main>
  );
}
```

These fill gaps the spec and the contracts leave open. Each is small and reversible.

| Topic | Decision | Why |
|---|---|---|
| Env key name | `DISCORD_APP_ID` (contract §4.3), the key the user already has in `apps/server/.env` | The contract's names are normative and match the user's file, so no `.env` file is edited |
| Infra env | The five names join `packages/infra/.env.schema`'s `@import(../../apps/server/, pick=[...])` list; no value is copied | varlock reads picked keys' values from `apps/server/.env`, as it already does for the PayPal and SMTP keys (Fact 17); copying values would edit a user secrets file |
| API version | `https://discord.com/api/v10` everywhere | Available and current (Fact 6); v9 would also work but gains nothing |
| Command registry | Global commands only, published with the bulk `PUT` | Contract §4.3 says global; the PUT also prunes removed commands. Global commands take a few minutes to propagate — noted in the walkthrough |
| Deferral policy | `/payouts setup` answers immediately (type 4, ephemeral); `/payleor link` always defers (type 5 + EPHEMERAL) and PATCHes the original response | The dispatcher supports both paths (Fact 4/5); linking touches the database, and deferring is the pattern every later command with real work reuses |
| Deferred db connection | The route opens its own connection for the follow-up and closes it there | The middleware's db ends with the response (Fact 19); a dedicated connection removes the ordering hazard |
| Code consumption order | `/payleor link` consumes the code first, then checks the Discord link and the team role | The delete is atomic and one-time (no replay races); a code burned by an unauthorized caller costs the admin one click |
| Guild conflict check | Pre-check `findTeamIdByDiscordGuildId`, unique index as the backstop | A caught unique-violation is brittle to detect through drizzle's error wrapping; the index still guarantees one team per guild if two links race |
| `discord_link_code` shape | `id`, `team_id`, `code` (unique), `expires_at`, `created_at`, consumed by deletion | The contract names the table only; deletion makes one-time-ness atomic and keeps the shape minimal |
